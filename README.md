Hybrid Toy Project — DB 담당자 활동 요약

온프레미스(OKD)와 AWS 클라우드를 Cloudflare로 연결하는 하이브리드 의료 서비스 뼈대 구축 프로젝트. 4인 팀에서 DB 설계·보안·운영을 담당했다.

프로젝트 개요

병원 예약·진료·처방 시스템을 가정한 팀 프로젝트로, 외부 환자용 서비스(ALB 경유)와 내부 직원용 서비스(사내망 → Cloudflare Tunnel 경유)를 하나의 백엔드로 통합하는 구조를 목표로 했다.

환자 → Cloudflare(WAF) → ALB → BFF → WAS → RDS
직원 → 사내망 → Cloudflare Access/Tunnel → cloudflared → BFF → WAS → RDS

팀은 인프라 리드(Terraform/AWS), EKS팀(WAS/BFF/Web 3인), DB팀(본인)으로 구성됐고, 본인은 DB 설계·계정 보안·데이터 적재를 전담했다.

담당 업무
1. 스키마 설계 및 확정

기존 예약 도메인(환자, 직원, 예약)에 진료·처방 도메인(차트, 처방, 처방 항목, 상병코드 마스터)을 추가 설계했다. 특히 상병코드 마스터는 공공데이터 특성상 하나의 코드에 여러 명칭(동의어)이 붙는 구조라, 마스터 테이블과 동의어 테이블을 분리해야 한다는 것을 데이터 실측(동일 코드에 명칭 60건 존재)을 통해 확인하고 반영했다.

2. 계정 권한 최소화 — 테이블 단위 화이트리스트

애플리케이션 계정에 스키마 전체 권한을 부여한 뒤 필요 없는 부분만 회수하려던 초기 설계가 구조적으로 불가능하다는 것을 실측으로 확인했다.

ERROR 1147 (42000): There is no such grant defined for user 'app_was'
                     on host '%' on table 'icd_code'

MySQL은 DB 단위로 부여한 권한을 테이블 단위로 회수할 수 없다는 것을 직접 겪은 뒤, 처음부터 테이블별로 필요한 권한만 명시 부여하는 화이트리스트 방식으로 전환했다. 참조 전용 마스터 테이블(상병코드)에는 SELECT만 부여해, 애플리케이션이 런타임에 마스터 데이터를 건드릴 수 없도록 권한 자체로 강제했다.

3. 인증 정보 보호

비밀번호는 평문 없이 BCrypt 해시로만 저장했고, 컬럼 타입(CHAR(60))으로 해시 형식을 강제했다. RDS 접속 구간에는 TLS를 강제(REQUIRE SSL)하고, 실제 암호화 여부를 SHOW STATUS LIKE 'Ssl_cipher'로 검증하는 절차를 세웠다.

4. 데이터 무결성 — DB 제약을 최종 방어선으로

예약 중복, 처방 중복 발급 같은 동시성 문제를 애플리케이션 로직만으로 막지 않고, UNIQUE 제약을 최종 방어선으로 설계했다. 애플리케이션 계층의 사전 체크는 UX 보조 수단일 뿐이라는 원칙을 지켰다.

5. 대용량 공공데이터 적재

공공데이터포털의 상병코드 원본(약 4.8만 행)을 가공해 적재했다. 원본의 필터 조건 값이 의미상 반전되어 있다는 것('N'이 정상값)을 발견해 필터를 교정했고, 결과적으로 마스터 14,283건 · 동의어 37,543건으로 분리 적재했다. 검색 성능을 위해 인덱스 3종을 함께 설계했다.

6. 시크릿 관리 및 협업 규칙 준수

DB 자격 증명을 코드나 Terraform 변수에 하드코딩하지 않고 AWS Secrets Manager로 조회하도록 했다. 로컬 작업 시 실행용 파일과 커밋용 원본 파일을 분리해, 비밀번호나 해시가 git에 남지 않도록 관리했다.

협업 지점
WAS 담당에게 DB 접속 정보와 스키마 변경 사항을 즉시 전달하는 방식으로 개발을 병행했다.
인증·인가는 BFF가 JWT 발급/검증을 전담하고 WAS는 DB 조회와 비밀번호 검증만 담당하는 역할 분리 계약을 지켰다.
인프라 팀이 구성한 네트워크 격리(사설 서브넷 + 클러스터 내부 임시 파드 경유) 구조 위에서, 그 환경에 맞춰 DB 계정 보안을 설계했다.
배운 점

권한이나 네트워크처럼 "나중에 좁히면 된다"고 생각하기 쉬운 설계는 실제로는 되돌리기 어려운 경우가 많다는 것을 직접 겪었다. 이후로는 설계 초기에 최소 범위를 먼저 정하고, 필요할 때 확장하는 순서로 접근하는 습관이 생겼다. 또한 스크립트가 성공했다는 결과를 그대로 믿지 않고, SHOW GRANTS처럼 실제 상태를 조회해 재확인하는 습관을 이 프로젝트에서 만들었다.
